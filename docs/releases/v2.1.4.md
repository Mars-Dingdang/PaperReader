# PaperReader v2.1.4

> 📖 **Read the [User Guide (中文)](https://github.com/Mars-Dingdang/PaperReader/blob/main/docs/user_instruction.md) before downloading** — installation, first-run setup, and usage. [中文发布说明](https://github.com/Mars-Dingdang/PaperReader/blob/main/docs/zh-cn/releases/v2.1.4.md)

PaperReader v2.1.4 makes the Windows application reliably startable, fixes Chinese rendering in translated PDFs, and marks Windows as an officially supported platform.

## What's fixed

- **Windows window startup.** Earlier v2.1.x Windows packages could fail before any window appeared: the (unpinned) build dependency `pythonnet` resolved to 3.1.0, whose `Python.Runtime.dll` cannot be initialized by the .NET Framework host inside a PyInstaller-frozen app, so the launcher logged `Failed to resolve Python.Runtime.Loader.Initialize` and exited. The desktop window stack is now pinned to `pythonnet 3.0.5` + `clr-loader 0.2.7.post0`, which initialize correctly in the frozen EXE. Windows users on any earlier v2.1.x build should switch to the v2.1.4 ZIP.
- **Local Windows builds crashed at EXE startup** with `ModuleNotFoundError: No module named 'backports'` when the build environment had setuptools 80.x: PyInstaller bundles setuptools' vendored `jaraco.context`, whose `from backports import tarfile` (Python < 3.12) was missing from the frozen graph and killed the `pkg_resources` runtime hook before the app started. Windows build environments now pin `setuptools 65.5.0` — the same version CI's setup-python provides — whose `pkg_resources` is self-contained.
- **The release smoke test now covers the packaged GUI stack.** It previously launched the packaged backend with `PAPERREADER_NO_WINDOW=1`, which skips `webview` entirely; that is how a broken window shipped green in v2.1.1. The packaged EXE is now additionally run once with `PAPERREADER_GUI_CHECK=1`, which initializes `webview.guilib` (pythonnet/.NET + WebView2 bindings) without opening a window, and a nonzero exit fails the release.
- **Portable packaging robustness.** `desktop/build_portable.ps1` stops a still-running portable app before rebuilding (a running `PaperReader.exe` keeps `dist\PaperReader` locked) and retries ZIP creation, fixing `Compress-Archive` failures such as `base_library.zip 正由另一进程使用` when a freshly written file is held briefly by antivirus or the shell.
- **No more mojibake in the portable ZIP on Chinese-locale Windows.** `build_portable.ps1` and `create_shortcut.ps1` are saved as UTF-8 with BOM, so Windows PowerShell 5.1 reads their Chinese literals correctly: the in-ZIP `使用说明.txt` keeps its proper name and the desktop shortcut keeps its proper description.
- **Chinese text is visible in translated PDFs inside PaperReader.** XeLaTeX correctly embedded the translated CJK glyphs, but the PDF.js viewer did not ship or load its packed Adobe CMaps, so CID-keyed fonts such as TeX Live's Fandol appeared as blank space. The frontend now bundles the PDF.js CMaps and standard font data and supplies their URLs to both the reader and artifact-preview renderers. Newly translated documents also prefer Windows' SimSun font before the macOS, Linux, and TeX Live fallbacks.
- **LaTeX compilation no longer flashes terminal windows on Windows.** The packaged app starts `latexmk` with `CREATE_NO_WINDOW`; the same protection covers the optional MinerU `curl` fallback.

## Compatibility

This is a backward-compatible patch release and requires no data migration. Windows 10/11 x64 with the WebView2 Runtime (built into most current systems) remains the target; TeX Live with `latexmk` and `xelatex` is still required only for translated PDF generation. macOS requires Apple Silicon and macOS 13+.

## Verification

The packaged EXE built with the pinned window stack was launched on Windows 11: the backend became healthy at `127.0.0.1:8000` and the native WebView2 window opened. The archive smoke test (`scripts/smoke_release.py --archive`) asserts the `/health` version against `frontend/package.json` and runs the packaged EXE once with `PAPERREADER_GUI_CHECK=1`, so a frozen build whose .NET bridge or WebView2 bindings fail to initialize cannot pass CI. Regression coverage also checks the Windows `latexmk` creation flags and the cross-platform CJK preamble fallbacks; the frontend build verifies that the viewer configuration and copied PDF.js assets compile together.
